## 1. 现状机制图（代码级已核实）

| 机制 | 覆盖面 | 动作 | 触发方式 |
|---|---|---|---|
| 主动余额查询 `CNProviderBalanceCheckService` | **仅 kimi/deepseek**（`platforms()` 硬编码） | 真实 `QueryBalance` → 低于阈值 `SetTempUnschedulable`（`cn_balance_low` 前缀，2×探测周期≈20min）→ 恢复自动清 | 周期 |
| 配额窗口探测 `probeQuota` | zhipu/minimax/volcano | 只写 Extra 快照，**明确不做停调决策**（代码注释："调度阈值评估读取快照统一判定"） | 周期 |
| 余额不足反应链 | 全部 CN 供应商 | 真实请求失败文案匹配 → `handleCNProviderInsufficientBalance` → 停调 20min | **被动**（真实请求吃 402/文案） |
| 窗口耗尽反应链 | CN 供应商 | 真实请求吃 429 → 快照任一窗口 ≥99% → `SetRateLimited` 冷却到窗口重置点（`cn_provider_quota_window_rate_limited`） | **被动** |
| 阈值停调 `ApplyAccountSchedulingThreshold` | 多平台 | 快照用量 ≥ 管理端阈值 → 停调到窗口重置点；CN 平台**只在选号时惰性评估**（周期调用先例仅 codebuddy 平台） | 惰性 |
| 停调通知 `notifyAccountSchedulingBlocked` | 全部 | 仅进程内运行时快速阻断，无管理端告警 | — |

关键结论：
- #58（zhipu 官网订阅，周窗口打满）：走"被动窗口反应链"停到 09-27 00:16（周重置）。
  调度上已排除出池，但停调依赖一次真实请求先吃 429，低流量时段账号被反复选中
  反复失败；且无任何告警。
- #82（zhipu 平台挂 TeamoRouter 中转钱包）：**无任何主动余额查询**。钱包死 → 只能等
  真实请求 402 → 停 20min → 再拿真实请求试错，无限循环；充值恢复也无探测可自动闭合。
- 同型波及：#38/79/80（当日福利额度耗尽）、#47/49（第三方 credits 尽）、#32/33（火山月配额停放至 10-04）。

## 2. 原设计目录（全平台实证，本次修复的对齐基准）

1. **统一停调原语 = `temp_unschedulable`（带原因前缀，到期自动恢复或探测恢复清除），
   从不自动翻转 `schedulable`/`status`**。证据：kimi/deepseek 余额、codebuddy、
   OpenAI 阈值+auto-reset、grok free 软门禁、anthropic fable、CN 反应链、健康熔断 L3。
2. **周期探测骨架 = `CNProviderBalanceCheckService` 的 Start/Stop/runOnce + ticker**，
   codebuddy 服务克隆它。扩平台=在既有服务内扩分支，不建新服务。
3. **停调决策统一入口 = `ApplyAccountSchedulingThreshold`**，周期探测后调用有现成先例
   （codebuddy_quota_check_service.go:119）。
4. **管理端告警 = `OpsAlertEvaluatorService` 规则引擎**；指标 `account_temp_unscheduled_count`
   **已存在**（全 reason 聚合——作者既有粒度，沿用，不按 reason 拆新指标）。
5. **zhipu 系余额检测语义 = 响应 402/余额文案匹配**（`cnProviderResponseIndicatesInsufficientBalance`）。
6. **停调原语并发语义**：`SetTempUnschedulable`（account_repo.go:2422）SQL 守卫**只延不缩**；
   `ClearTempUnschedulable`（:2499）无条件清除，作者的防误清设计是服务层前缀守卫
   （cn_provider_balance_check_service.go:255）。
7. **协议构造与模型解析 SSOT**：`AccountTestService` CN 探测链
   （account_test_service_cn_adaptive.go；出站校验 `cnValidateProbeURL`）；
   模型解析 = `resolveWebTestModel`（account_test_service.go:675，显式→映射→平台默认）。
8. **原设计对其周期探测不设逐账号门禁/指纹/漂移守卫**：kimi/deepseek 账号全部被
   周期查询，查询失败仅记日志下周期重试，无任何启用位或状态簿记。本方案新路径
   承担**同一风险姿态**（对齐裁定：遵循原设计，不过度设计）。
9. **部署形态 SSOT**：`deploy-config/sub2api-ops.md`——单容器 docker compose（sub2api），
   单实例部署；版本回退走既有发布路径。

## 3. 修复方案

**对齐原则（用户裁定）**：新探测路径与既有 kimi/deepseek 路径承担同一风险姿态——
不新增运行时开关、逐账号状态或回滚簿记；付费探测的授权以**阶段门**控制
（确认包授权后方可派发部署），部署即启用，与既有服务行为一致。

### 3.1 缺陷②：余额查询覆盖所有 CN 供应商账号
在既有 `CNProviderBalanceCheckService` 内扩展（不动骨架），探测机制复用 §2.7 既有
`AccountTestService` CN 探测链：
- kimi/deepseek：维持现状（原生余额 API），零改动。
- zhipu/minimax/**volcano**/中转钱包账号（R16-F1：覆盖集合以现状机制图 §1 为准，
  volcano 不豁免）：周期**最小完成请求探测**（max_tokens=1，最小输入；
  模型经 §2.7 `resolveWebTestModel` 链解析，解析失败 → 本轮跳过 + 日志，下周期重试；
  出站校验 `cnValidateProbeURL`；每周期读取账号**当前**凭证/配置发起——无缓存指纹，
  与既有服务读取姿态一致）。不用 GET /v1/models（智谱 payg 余额为零时仍 200，不可靠）。
  **模型可解析性（R17-F1）**：范围内账号在阶段 0a 以同一 `resolveWebTestModel` SSOT
  **只读核验**——确定性无法解析（无显式模型/映射/平台默认）→ 阻断部署，或经用户
  明示豁免并同步收窄 Done-when；运行时"解析失败 → 本轮跳过 + 日志，下周期重试"
  仅承接受态，不作为永久未覆盖账号的宣称依据（不新增运行时机制）。
  volcano 是否存在原生余额查询语义由阶段 0a 沿权威链核实：有 → 走原生路径
  （同 kimi/deepseek）；无 → 纳入最小完成请求探测；证据矛盾或缺失 → 列确认包阻断项。
- 响应判定唯一入口 = 既有 `cnProviderResponseIndicatesInsufficientBalance`/402
  ——**余额判定第一且唯一入口**（含 429 携带余额文案的重叠情形，命中即走余额停调）：
  - 命中 → 走既有 `handleCNProviderInsufficientBalance` 停调 20min；
  - 未命中且为有效完成响应 → 按既有 :255 前缀守卫模式精确清除自家
    `cnBalanceLowReasonPrefix` 停调（写入与清除同一常量——充值后自动恢复）；
  - 其余（超时/连接失败/401/403/未识别错误体/解析失败）→ 保持现状 + 既有错误
    观测日志，下周期重试（与 kimi/deepseek 探测失败的既有姿态一致，不停调、不清除、
    不新增猜测式匹配）。
- **平台耗尽特征核实（一次进确认包，不做逐账号登记）**：zhipu 官网 402/文案以
  生产事故证据（#58/#82 即现成实证）+ 官方文档核对；minimax/volcano 同法；中转
  钱包按平台逐一核对。**既有判定器无法识别耗尽语义的平台/中转 = 失败关闭阻断项
  （R16-F2，禁降级）**：该平台不纳入本次探测分支，相关账号**明确退出"所有账号"
  覆盖范围须经用户裁定**（补证或明示豁免并同步收窄 Done-when），不得以"退回被动
  反应链、状态不劣于现状"作为降级路径宣称覆盖；确需活体实测补证的平台 → 连同
  消耗上界一并列入确认包授权，无授权不发请求。
- **成本边界（R18-F1）**：措辞 = **检测不牺牲真实用户请求**（探测自身消耗另计）。
  `max_tokens=1` 仅限输出上限，**不等于单次仅 1 token**——阶段 0a 按各平台权威
  计费与限额单位核算**单次与每日最坏上界**（至少含：输入、输出、最低计费量、
  按请求计费、RPM/RPD 配额占用），核算结果随确认包送用户授权；无授权不派发。
  无需新增运行时机制。

### 3.2 缺陷①：额度打满的订阅号主动熔断
- `probeQuota` 落快照后调用既有 `ApplyAccountSchedulingThreshold`（照抄 codebuddy
  先例 :119 调用方式）。窗口用量 ≥ 管理端配置阈值 → 一个探测周期内停调到窗口
  重置点，不等真实 429。恢复 = 窗口重置自动到期（既有机制）。评估规则零改动，
  **不发明默认阈值**。
- 缺失阈值账号：经既有管理端补配（提案值随确认包送裁）；验收时仍无阈值且未经
  用户裁定豁免 → 缺陷①对该账号未闭合（阻断项）。
- 单元测试"无阈值不停调"为既有语义保持，非缺陷①验收项。

### 3.3 告警（R17-F2：移出本任务，另案）
- 用户权威范围 = 两项缺陷；原设计对停调**无管理端告警**（§1：notifyAccountSchedulingBlocked
  仅运行时快速阻断）。全 reason 聚合规则会对**其他原因**造成的停调触发新通知行为，
  超出本任务边界。告警规则部署与链路验收移出本任务；如需告警治理另案送裁
  （零代码、纯管理端配置，可独立执行）。

### 3.4 实施阶段结构
- **阶段 0a（派发前置·纯只读）**：账号与阈值盘点、平台耗尽特征取证（官方文档 +
  既有生产事故证据）、探测成本核算——产出冻结后形成**用户确认包**一次送裁。
  零真实上游请求。
- **用户裁定**：确认包各项 + 实施批准。
- **阶段 1（代码实施派发）**：按裁定结论派发编码（文件+测试对粒度）。
- **阶段 2（部署启用与验收）**：部署即启用（既有服务行为）、链路集成验证、证据落盘。

**回滚（对齐既有发布实践，不建状态簿记，R18-F3）**：版本回退（既有单容器发布
路径，§2.9）即同时移除两条新增代码路径（探测与阈值调用同版发布、同版回退）；
本任务新增的补配阈值经既有 UI 移除即恢复（**仅限确认包记录的本任务写入项**，
不触碰他任务或既有配置）；回退时运行中的停调按原设计语义自然到期（20min/窗口
重置，**有界**），与既有全平台机制回退姿态一致。

## 4. 边界（本方案不做）

- 不自动翻转 `schedulable`/`status`；不新增 status 枚举；不建新周期服务；不新增
  停调原语变体；不新增告警指标；不新增协议判定/模型解析/余额文案匹配逻辑；
  不发明默认调度阈值；不改既有冷却参数与阈值评估规则。
- **不新增**逐账号探测门禁、身份指纹/IfMatch 校验、漂移守卫、状态簿记回滚——
  原设计对同类周期探测无此机制（§2.8），新增即违反对齐裁定与不过度设计裁定。
- 告警规则部署与链路验收不在本任务范围（R17-F2，另案送裁）。
- 不动 `upstream_billing_probe`；组内绑定优先级问题另案。

## 5. 验收口径（Done when）

1. **缺陷②行为验证**：覆盖集合 = 确认包核验通过的平台清单（zhipu/minimax/volcano/
   中转；含用户明示豁免记录，无隐式遗漏——R16-F1/F2）。清单内账号余额死 → 一个
   探测周期内停调；充值 → 下个周期自动恢复；检测不牺牲真实用户请求。定向测试
   覆盖停调/恢复/文案识别三分支。
2. **缺陷①行为验证**：配置阈值账号窗口触顶 → 一个探测周期内停调到窗口重置点
   （不依赖真实 429）。zhipu/minimax/volcano 参数化：未触顶不停、触顶停调、重置
   恢复；既有更长停调不被缩短；"无阈值不停"仅作语义保持单元测试。
3. **响应矩阵测试**：判定优先级正反重叠用例（429+余额文案 → 停调；429 无文案 →
   保持现状）；**重叠用例须断言实际进入余额分支（R18-F2）**：余额 reason 前缀 +
   ≈20min 期限 + 未写入配额窗口原因 + 后续有效探测清除该前缀；前缀精确命中
   （先不足写入、再有效清除断言）；原生/中转参数化；模型解析失败跳过 + 日志。
4. `go build` + 定向测试 + 类型检查通过；收敛阶段全量构建一次。
5. 证据按 `docs/evidence-filing-standard.md` 落盘（确认包与授权记录、成本核算、
   阈值配置记录、模型可解析性核验记录）。
