# Kimi 上游故障切换与熔断加固方案

日期：2026-09-26（v4：第 3 轮外审消化 + 根源性澄清；v3：定位"升级既有机制，非新建"）
状态：闸①闭合（第 3 轮消化记录 + 用户裁定 6），进入并行派发
背景：corealgos Kimi 号池（#52-#56，上游 infer 中转）在 infer 源站故障期间（CF 代答
520/522/524）反复 524，每跳等上游 CF 90~125s 超时，串行 failover 跑不赢客户端 CF
~100s 首字节死线。

## 定位声明（v3 核心：升级，非新建）

本方案全部落点为项目作者既有机制的入口开放与参数调整，不新建任何平行机制：

| 方案项 | 项目作者既有机制（生产实证已在运行） | 改动性质 |
|---|---|---|
| P1a 快速冷却 | fastpath 瞬态冷却 `shouldCooldownOpenAITransientUpstreamError`（openai_account_runtime_block_fastpath.go:204）本就含 500/502/503/504/520-524 | 拆平台门禁（:183-185），对 CN 家族开放既有入口 |
| P1b 滑窗熔断 | 健康熔断器 `openai_apikey_health_breaker`（L1 watch/L2 warning/L3 trip）scope_platforms 本就含 kimi 且已启用 | **纯管理端配置调整，不改码** |
| P1c 恢复 | `AccountHealthRecoveryProbeService` 主动探测（生产 probe_attempts=5 实证已在跑） | 新停调标记词加入既有 probeRecoverableMarkers |
| P2 首包超时 | 既有出站 client | 加超时参数；超时错误走既有 failover 链 |
| P3a 同账号重试 | `GetPoolModeRetryCount`/`effectiveSameAccountRetryLimit` 既有读取链 | 默认常量 3→1 |
| P3b 旧链 | `maxAccountSwitches` 旧配置 | 删除归零（合同 §4） |
| P4 源站切断 | 与健康熔断器 L3 语义重叠 | 不建平行机制；若实施作为健康熔断器 host 维度扩展演化，独立阻断待裁定 |

## 根因记录（v3 更正版——更正 v2"整条链被挡死"的不完整结论）

**生产 DB 实证（2026-09-26）**：健康熔断器本来就覆盖 kimi 且已启用，#53/#54/#55/#56
在故障窗口（2026-09-25 18:24~18:38 UTC）全部被 L3 跳闸过（matched_keyword=
openai_apikey_health_breaker，4次/5min，tier 3，probe_attempts=5 探测也跑了）。
"零熔断零恢复"的早期结论不完整，予以更正。

真实问题三层：

1. **参数与故障形态不匹配**：熔断阈值 4次/5min，但每跳失败要等上游 CF 90~125s
   才暴露，失败率被时间摊薄，多数时段够不到阈值——仅峰值时刻跳闸，故障大部分
   时间账号留在池里持续吃请求；
2. **跳闸后恢复链太弱**：冷却仅 5min，探测 60s 间隔 × 5 次≈5min 全落在源站故障
   期内后放弃，TTL 到期回池继续吃请求——"恢复监测"存在但在长故障中失效；
3. **fastpath 单发瞬态冷却（第二层缺口）**：第一跳 520-524 本应立即罚 2min 冷却
   （早期快速摘除失败账号），被平台门禁（Platform==OpenAI && APIKey）挡住，
   kimi 吃不到。三道门结论对 fastpath 层仍然成立。
4. 观感干扰：账号 status 列显示 active 造成"从没熔断"假象（temp_unschedulable
   是独立机制，不反映在 status 列）。

另：12h 聚合 524 ×197、520 ×46、502 ×31；502 来源已查明为上游原始 502
（ops_error_logs 实证，非网关合成），既有冷却集合已含 502。

## 用户需求（权威，2026-09-26 口述，6 条）

1. 账号轮询不要限制个数，所有有效账号都要轮询到；
2. 重试限制调低，账号不行了赶紧轮询下一个；
3. 失败账号保持测试，一旦恢复马上启用；
4. 单账号超时要更短（初始提案 30s → 数据调研 → 用户裁定 **60s**）；
5. 上游故障时可同时切断同源站所有账号，但必须分清源站整体故障 vs 单账号问题；
6. 查清一直没有熔断的根因（✅ 已查明并更正，见上）。

### 用户裁定累积（2026-09-26）

| # | 裁定 | 内容 |
|---|---|---|
| 1 | P2 阈值 | 60 秒 |
| 2 | 重复计费 | 接受上游重复计算代价，换快速切换；本地不向用户重复计费（无响应不记 usage，既有计费事实源语义），不做对账机制 |
| 3 | 恢复监测 | 接入主动探测（复用既有 AccountHealthRecoveryProbeService） |
| 4 | 同账号重试 | 默认 3→1 同意 |
| 5 | 健康熔断器参数 | 4次/5min → **2次/5min**；冷却 5min → **15min**（纯配置） |
| 6 | 流程裁定 | 第 3 轮外审 6 条经甄别均非实质方案缺陷：无实质缺陷不重复外审，闸①以消化记录闭合，直接进入并行派发；外审建议须甄别过度设计，问题从根源解决，不叠补丁（2026-09-26） |

**裁定 5 的作用域说明（用户知情点）**：健康熔断器参数为 6 平台共享设置
（openai/deepseek/kimi/zhipu/minimax/other 同值），2次/5min + 15min 对 OpenAI
自身同样生效。按用户裁定全局执行；如需 OpenAI 保持原值须另行裁定。
**派生的配置对齐项**：冷却 15min 下，探测 60s 间隔 × max_attempts 必须 ≥15min
（max_attempts ≥15，纯配置），否则探测在冷却结束前放弃、违背需求③。
推导依据（第 3 轮外审第 2 条闭合，代码实证）：探测服务用 `time.NewTicker`
（account_health_recovery_probe_service.go:124-137），首跳在 t=60s 而非 t=0，
15 次尝试覆盖 t=60s~900s，第 15 次恰好落在 15min 冷却边界，窗口闭合。

## 方案

### P1 熔断增强 = 既有三层机制升级（需求 2/3/6）

**范围（第 2 轮外审第 1 条收敛）**：显式清单 kimi/deepseek/zhipu/minimax
（apikey+oauth，与 OpenAI 共用 `handleOpenAIAccountUpstreamError` 单点出站链）。
**`other` 剔除**——生产实证 other 平台含 openrouter（apikey）与 8277 oauth、
星思云混合账号，非封闭 CN 中转家族，纳入会越权。OpenAI 行为不变；
anthropic/gemini/codebuddy 独立出站链不碰。

**P1a fastpath 平台门禁拆除**（既有机制开放入口，零新机制）：
- `handleOpenAIAccountUpstreamError`（fastpath:183-185）瞬态冷却门禁：显式清单
  平台纳入（保留池模式豁免逻辑）；
- `BlockAccountScheduling`（:327）`isOpenAIAccount` 早退：显式清单纳入；
  内存 CAS+TTL 语义不变；
- 429/402/529 既有 CN 语义链不动，只补 5xx 空档。

**P1b 健康熔断器参数调整**（用户裁定 5，纯管理端配置，不改码）：
- failure_threshold 4→2（次/5min 窗口不变）、cooldown_minutes 5→15；
- 派生对齐：probe.max_attempts ≥15（见裁定 5 说明）；
- 实施时核对生产 settings 当前值与部署链路（管理端 API/DB）；
- 改前记录旧值快照；回滚方式 = 管理端将对应键设回旧值（无仪表盘/对账等新机制）。

**P1c 探测恢复链接入**（用户裁定 3，复用唯一探测服务）：
- **实施裁定（2026-09-26，派发卡 3 BLOCKED 顶回后主会话裁定）：P1c 零码改闭合**。
  依据：①P1a 瞬态冷却为 model 级内存块，TTL 10s/45s < 探测间隔 60s，自然到期
  即恢复，探测构造性 no-op；②长冷却场景（健康熔断器 L3，裁定 5 后 15min）账号
  落 DB temp_unschedulable 且 matched_keyword=openai_apikey_health_breaker 已在
  既有 probeRecoverableMarkers 白名单，探测恢复链本来就通（生产实证 #53-56
  probe_attempts=5 已跑）；③无新停调标记词产生，不臆造常量、不建第二条枚举路径。
- 需求③闭合路径：短冷却自然到期（秒级恢复）+ 长冷却既有探测提前恢复
  （60s 间隔 × max_attempts≥15，派生配置对齐项）；

### P2 CN 平台上游首包超时 60s（需求 4，用户裁定）

数据（usage_logs.first_token_ms，成功请求口径）：kimi-k3 14 天 9,677 笔
p50≈20s、>30s 26.9%、>60s 4.0%、>90s 0.6%；deepseek >30s 10.7%、>60s 2.6%。
30s 误杀 27% 不可行；60s 误杀 4%（用户裁定确认）。

**计时边界定义（第 2 轮外审第 3 条闭合）**：
- 起点 = 出站请求发出；终点 = **上游响应 body 首字节**（仅收到响应头不停止计时）；
- 触发动作：60s 到期 = 取消当前上游尝试（context cancel，复用既有取消链），
  错误映射为既有 failover 循环可消费的 NextAccountRetry 错误；响应头已下发
  给客户端后不做透明切换（此时切换对客户端不可见，仅按既有流中断语义处理）；
- 首包到达后流式传输不受影响；OpenAI/Anthropic 官方长思考流不适用；
- 定向测试锁定三场景：①仅有响应头无 body；②59s 首数据后长流正常；
  ③客户端提前取消。

时序口径：单跳 60s 超时 + failover 下一跳正常首包（p50≈20s）≈80s 完成；双跳
均超时由客户端 CF 自行切断（现状语义，不劣化）。重复计费语义见裁定 2。
**拒绝项留痕**："剩余 deadline 预算扣减机制"拒绝——客户端 CF 超时为不可知
外部值，实现只能靠假设，违反合同 §1 零假设/§5 禁兜底。

### P3 切换上限旧链归零 + 同账号重试默认 3→1（需求 1/2，用户裁定 4）

- **删除 `maxAccountSwitches` 整条旧链**（gateway_handler.go:56 常量 +
  cfg.Gateway.MaxAccountSwitches 配置 + 文档 + 部署值），新语义：每账号至多
  尝试一次 + 失败排除列表、无固定上限（闸②终审第 4 条"冻结请求开始时候选
  集合"已裁定拒绝：属新机制，且请求期间恢复/新增账号可被尝试恰服务于
  需求①，合同 §5 改动最小化）；完成前残留扫描；
- **同账号重试默认 3→1**：`defaultPoolModeRetryCount`（account.go:1105）3→1；
  failover_loop.go:37 兜底默认 `maxSameAccountRetries` 同步 3→1；显式
  `pool_mode_retry_count` 覆盖与 `SameAccountRetryMax` 硬上限维持既有语义；
- 失败序列测试证明：不可重试错误第一跳即切下一账号，不发生同账号二次尝试。
- **有意边界（第 6 轮外审 residual_risk 处置，2026-09-26）**：模型发现
  （models list）的 scheduler fallback 在 `openai_models_list.go` 保留独立的
  固定 3 次账号预算（`maxFetchSwitches<=0` 时最多尝试 4 个账号）。本方案
  v4 的"候选集合耗尽才终止"语义显式清单为**平台请求 failover 链**；模型
  发现是辅助探测路径，不在需求①"账号轮询不限制个数"的语义范围内，其
  fallback 预算为有意保留的独立边界，不做代码改动（第 6 轮外审给出的第二
  选项：单一权威文档记录为有意边界）。

### P4 同源站整体切断（需求 5）——维持独立阻断，不建平行机制

与健康熔断器 L3 语义重叠；若实施，唯一正解是健康熔断器的 host 维度扩展演化
（同一状态机加聚合维度），不得另起平行熔断。实施前必须由用户裁定：
- 判定含正向故障证据（已知正常账号的同窗口失败观测）；
- 完整状态转移表：同源站标识、窗口长度、失败阈值、正常账号判定来源、开路期
  并发请求处理、唯一半开执行者（探测账号选取、并发互斥、CAS 转移、成功/失败
  转换）、可观测指标。

## 实施顺序

1. P1a+P1b+P1c（三层既有机制升级：门禁拆除 + 纯配置调整 + 探测标记接入）；

P1~P3 属调度/状态机高风险边界（合同 §6 独立复审）：方案审（闸①）通过后按
multi-agent-dispatch 拆单并行派发（文件+测试对，最大并发≤5），实现完成后送
终审（闸②）；生产实测证据按 docs/evidence-filing-standard.md 落盘。
